## Plan: Strip `<environment_context>` from Codex input + diagnostic test

### Background

Investigation shows chatgpt-web tool calling fails consistently after a successful first call. Root cause hypothesis: Codex 0.142.5+ injects `<environment_context><cwd>...<workspace_roots>...</environment_context>` into its `input` array. ChatGPT Web treats this as a hint that it has direct filesystem access and tries to use its own internal workspace connector (which 502s) instead of emitting `<tool>` blocks per OmniRoute's TOOL USE PROTOCOL.

User confirmed: even a **fresh cdx session** fails when sent "can you use the tool?" — so historical contamination is NOT the only cause. The env_ctx injection alone may be enough to derail the model.

### Goal

Strip the `<environment_context>` XML block from the Codex `input` array on the OmniRoute side (chatgpt-web path) so the model sees only the TOOL USE PROTOCOL + tool definitions. Verify the fix with concrete prompts.

### Phase 1: Add env_ctx stripper (chatgpt-web path)

**File:** `open-sse/executors/chatgpt-web.ts`

- Add a small helper `stripEnvironmentContext(input: Array<...>): Array<...>` that walks the input array, removes the `input_text` items whose `text` matches `<environment_context>...</environment_context>`, or strips the env_ctx substring from any item that contains it inline.
- Call it in `ChatGptWebExecutor.execute()` BEFORE `prepareToolMessages` is called, mutating the `bodyObj` in place (or returning a cleaned copy).
- Add a unit test `tests/unit/chatgpt-web-env-ctx-strip.test.ts` covering: (a) env_ctx as a standalone input_text item → removed; (b) env_ctx embedded in a user message → stripped; (c) multiple env_ctx items → all stripped; (d) input without env_ctx → unchanged.

### Phase 2: Run diagnostic tests from on-box

Run from SSH into `patty` (187.127.115.221), since I can reach that and the logs are there:

1. **Fresh session, no env_ctx, action prompt A**: `curl` chatgpt-web with single message "list the files in this directory and show me the README.md" → expect tool_calls delta.
2. **Fresh session, action prompt B**: "what's in the current directory?" → expect tool_calls.
3. **Fresh session, explicit bash prompt**: "run `pwd && ls`" → expect bash tool_call.
4. **Compare to July 6 baseline**: the same prompt that worked at 16:09:12 ("could you please read this project and let m e know what you think") sent fresh → check it still works.

If concrete prompts work but vague prompts ("can you use the tool?") still fail → it's a model prompt-interpretation issue, not a code bug.
If all prompts fail → the env_ctx strip wasn't sufficient; dig deeper into `parseOpenAIMessages` and the system-prompt serialization.

### Phase 3: Deploy and verify

- If Phase 1+2 shows the env_ctx strip helps, commit + push + deploy via `scripts/deploy-omniroute.sh --hostinger` (and `--contabo` if user wants staging).
- Re-run live tests from your `cdx` client.

### Out of scope

- Refactoring the larger pre-provider synthesis in `chatgpt-web.ts` and `webToolSynthesis.ts` (flagged by team-protocol as duplicated, but not the cause of the current regression).
- Updating Codex 0.142.5 behavior (we don't control it; env_ctx stripper is the OmniRoute-side workaround).
